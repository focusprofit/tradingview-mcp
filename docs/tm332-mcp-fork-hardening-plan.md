# TM-332 — tradingview-mcp: устранение трений, накопленных за сессию TM-328..331 (06-07.07.2026)

> Ветка `TM-332` (от `main`, локальный `main` уже на 13 коммитов впереди `origin/main` —
> не пушить без явного решения владельца по этим более ранним коммитам отдельно).
> Это НЕ продуктовый репозиторий `trademodel` — `/run`-Оркестратор сюда не
> распространяется (предполётная идентичность репо заточена на `focusprofit/trademodel`).
> Прецедент — TM-324 (`82a574c`): фикс трекается TM-тикетом в Jira, реализуется прямым
> коммитом в этот репозиторий, без orchestrator-loop.

## Контекст

За одну длинную сессию (TM-328→TM-331, 06-07.07.2026) MCP-форк создавал системное
трение при live-verify работе: минимум 3 отдельных stale-study инцидента, 2 попытки
main-агента вручную «найти кнопку» через слепой UI-обход (одна заблокирована
classifier'ом), 1 инцидент со снятием индикатора через сырой internal API (verifier),
1 инцидент со случайным кликом не туда (`Unflag symbol`). Владелец прямо запросил:
«форк надо масштабно доработать так, чтобы у тебя на руках были ВСЕ инструменты для
отладки» — не точечный патч, а системный проход.

**КЛЮЧЕВАЯ НАХОДКА уже при подготовке этого плана:** инструмент `ui_open_panel`
(`action: open/close/toggle`, `panel: pine-editor/strategy-tester/watchlist/alerts/trading`)
**уже существует** в форке (задокументирован в `CLAUDE.md` этого репозитория, строка 77)
— но НЕ был использован ни разу за всю сессию TM-331 (главный агент искал кнопку «Pine
Editor»/«Add to chart» слепым перебором `ui_find_element`/координатами вместо
`ui_open_panel(panel="pine-editor", action="open")`). Это меняет диагноз минимум для
пункта №7 ниже с «нет инструмента» на «инструмент есть, не был обнаружен/использован» —
приоритет №1 для проверки в первую очередь СЛЕДУЮЩЕЙ сессии, ДО любых код-изменений.

## §1 Реестр трений (пронумерован по степени боли за сегодняшнюю сессию)

1. **Нет add для приватного Pine-скрипта на график программно.**
   `chart_manage_indicator(action=add)` → `chart.createStudy(name, false, false, inputs)`
   (`src/core/chart.js`) — официальный Charting Library метод, не поддерживает
   invite-only/приватные скрипты ни по display-имени, ни по `script_id`. Подтверждено
   прямым тестом (TM-331). `remove` по `entity_id` работает для любого study.
   **Кандидат-фикс:** проверить, есть ли документированный сигнатурный вариант
   `createStudy` для custom studies (передача `{id, metaInfo}` вместо строки), ИЛИ
   найти именованный internal-метод, который вызывает кнопка «Add to chart» (см. п.7 —
   возможно решается через `ui_open_panel`+`ui_click` на найденной кнопке, без нового
   API вообще).

2. **Study залипает на старом байткоде после инжекта нового кода (stale-study).**
   3 независимых инцидента за сессию TM-331, разного масштаба (полное залипание /
   частичное после N часов / залипание сдвинулось на другую точку). Симптом:
   `data_get_pine_labels`/`data_get_pine_boxes` возвращают ОДИНАКОВЫЕ числа
   (`total_labels`/`excluded_unresolved`) до и после инжекта+компиляции нового кода.
   Существующее лечение — remove+re-add (ручное, см. п.1) — ненадёжно и медленно
   (3-5 минут ручного вмешательства владельца за инцидент).
   **Кандидат-фикс:** исследовать `chart.getAllStudies()[i].study().forceRepaint()` или
   аналог; проверить, помогает ли `chart_manage_indicator(remove)` +
   `pine_smart_compile`(на другом study) + программный `add` (см. п.1) быстрее ручного
   цикла; как временная мера — новый инструмент `pine_force_recompute(entity_id)`,
   пробующий несколько известных техник по очереди и явно репортящий, какая сработала
   (или что все не сработали — честный fail, не гадание).

3. **TM-324 (dirty-флаг) — уже НАЧАТ, не завершён.** Коммит `82a574c` на ветке
   `TM-324` — «inject via Monaco executeEdits instead of setValue» — сверить, смёржен
   ли в `main`, работает ли это на практике (сессия TM-331 всё ещё видела
   `verified:false` CRLF false-negative — возможно другой, смежный симптом, не тот же
   баг). Не переоткрывать заново — сначала проверить текущий статус фикса.

4. **`pine_set_source_from_file` даёт ложный `verified:false` из-за CRLF.** Monaco
   editor хранит `\r\n`, компаратор сравнивает сырые байты без нормализации →
   ложноотрицательный результат на КАЖДОМ инжекте в этой сессии (100% reproduction
   rate, не редкий edge case). Ручной воркэраунд (нормализация в Python на стороне
   агента) работает, но должен быть частью самого инструмента.
   **Кандидат-фикс:** нормализовать `\r\n→\n` на ОБЕИХ сторонах сравнения внутри
   `pine_set_source_from_file` перед вычислением `sha256_editor`, либо явно
   документировать/переименовать поле в `verified_raw` + добавить `verified_normalized`.

5. **`data_get_pine_boxes` — дедуп + обрезка по видимому диапазону viewport.**
   Возвращает боксы только из ТЕКУЩЕГО отрендеренного окна (см.
   `reference_data_get_pine_boxes_dedup_visible_filter`) — если viewport не там, где
   нужно (частый случай при stuck-at-realtime чарте), результат обманчиво пуст/неполон,
   не отличить от «реально нет боксов». Столкнулись с этим прямо в начале TM-331
   (chart_scroll_to_date не двигал viewport, только replay_start реально работал).
   **Кандидат-фикс:** опциональный `full_history: true` параметр, обходящий
   viewport-фильтр напрямую через данные study без завязки на что отрендерено.

6. **`draw_list` падает `getChartApi is not defined`** (известный баг,
   `reference_draw_list_getchartapi_bug_bypass`) — обходили через `ui_evaluate`
   `getAllShapes()`. В этой сессии `draw_list` ИНОГДА срабатывал напрямую (verifier
   в TM-331 отметил «сработал напрямую, обход не понадобился») — нестабильно
   воспроизводится. **Кандидат-фикс:** пофиксить сам баг в источнике (module-scope
   alias `getChartApi`/`evaluate`, см. commit `1ff456f` — возможно фикс неполный,
   баг всё ещё intermittent).

7. **Панель Pine Editor — не открывалась предсказуемо программно.** Потрачено
   огромное время на слепой UI-обход (`ui_find_element`, blind coordinates,
   `ui_evaluate` с ручным `.click()` — последнее корректно заблокировано
   classifier'ом). **`ui_open_panel(panel="pine-editor", action="open")` уже
   существует и не был использован — проверить СНАЧАЛА, есть шанс что это полностью
   решает пункт, без кода.**

8. **`chart_scroll_to_date`/`chart_set_visible_range` не двигают viewport, если
   чарт «застрял на realtime».** Работает только `replay_start`. Не всегда очевидно
   заранее, в каком случае какой инструмент сработает — агент тратит время на пробы.
   **Кандидат-фикс:** `chart_scroll_to_date`/`set_visible_range` должны либо явно
   форсить нужный переход (detect + auto-switch to replay if needed), либо чётко
   возвращать признак «не подействовало» (сейчас возвращают `success:true` с
   `requested`, но реальный `chart_get_visible_range` потом показывает другое — молчаливое
   несоответствие).

9. **`ui_click(by="class-contains", ...)` матчит НЕ тот элемент**, если класс общий
   для нескольких кнопок в одном контейнере (случайный клик по «Unflag symbol» вместо
   settings-gear индикатора). **Кандидат-фикс:** `ui_click`/`ui_find_element` — при
   множественных совпадениях возвращать список кандидатов с координатами ВМЕСТО
   автовыбора первого, чтобы вызывающий агент мог выбрать осознанно (или требовать
   явного индекса при >1 совпадении).

10. **Нет способа программно проверить «study точно свежая (не stale)»** без
    ручного сравнения счётчиков меток до/после (хрупкий, косвенный сигнал).
    **Кандидат-фикс:** новый read-only инструмент `pine_study_freshness_check`,
    сравнивающий текущий SHA-256 редактора с SHA-256, на основании которого study
    последний раз реально пересчиталась (если TradingView API это вообще
    экспонирует — требует разведки).

## §1.1 Прогресс сессии 07.07 ~14:40-15:10 (ветка `TM-332`, ждёт server-рестарт для live-verify)

**П.7 — ПОДТВЕРЖДЁН РАБОЧИМ вживую.** `ui_open_panel(panel="pine-editor", action="open")`
открывает Pine Editor корректно забинженным на текущий скрипт (проверено
скриншотом + `pine_get_source`). Остаточный модал «Open my script» закрывается
чисто через `ui_click(by="text", value="Close menu")` (найден однозначно через
`ui_find_element([class*="close"])`) — без blind-клика, без Escape.
`openScriptGui` (commit `43141d8`) теперь делает этот close ПОСЛЕ verified-свитча
сам, best-effort (не бросает, если панель уже закрылась).

**П.1 — РЕШЁН, root cause найден, live-подтверждён.** `smartCompile()` использовал
`/^add to chart$/i` (точное совпадение) для детекта кнопки «Add to chart», но
её `textContent` дублирован TradingView'ем самим («Add to chartAdd to chart» —
видимый лейбл + a11y-span оба попадают в textContent) → regex молча не матчил →
падало на fallback «Pine Save» (просто Save, БЕЗ добавления на график). Живой
тест: переключился на `Trade Model TEST (smoke)` (приватный, disposable
smoke-script, НЕ production DEV), напрямую кликнул найденную кнопку «Add to
chart» координатами из `ui_find_element` — study РЕАЛЬНО появилась в
`chart_get_state` (`tmFormat warm test`, entity `LYH3nd`). Убрано сразу после
теста (`chart_manage_indicator remove`), график вернул чистое состояние.
**Вывод: `chart_manage_indicator(add)` никогда не был правильным путём для
приватных скриптов — им и не должен становиться, `pine_smart_compile`
(после regex-фикса, commit `43141d8`) — штатный путь.** Regex сменён на
prefix-match (`/^add to chart/i`), как уже было у `compile()`.
**НЕ live-провалидирован ПОСЛЕ фикса** — сервер MCP (`node src/server.js`, pid
на момент сессии) не подхватывает код без рестарта, а рестарт роняет
MCP-соединение без автовосстановления в этой сессии
(`reference_mcp_server_kill_no_autorespawn`). Живой тест выше подтвердил
ПРИЧИНУ и что клик по правильной кнопке работает — не то, что сам
исправленный `pine_smart_compile` теперь кликает её (это лишь логически
следует из regex-фикса, не re-verified после рестарта).

**П.4 — фикс закоммичен (`8fa2ead`), НЕ live-провалидирован** (та же причина —
нужен рестарт сервера). `setSourceFromFile` теперь нормализует `\r\n→\n` на
обеих сторонах перед сравнением SHA-256 для поля `verified` (было — сырой
byte-compare, false-negative на КАЖДОМ инжекте в этой сессии); `verified_raw`
добавлен отдельно как старое сырое сравнение, для прозрачности.

**П.2 (stale-study) — ЧАСТИЧНАЯ разведка, БЕЗ фикса.** Read-only интроспекция
внутреннего PineJS-объекта study (`chart.getStudyById(id).study()`, класс `Ws`,
294 метода) нашла публичный (не `_`-приватный) метод `recalculate()`:
```
recalculate(){const e=this._model.paneForSource(this);
  this._model.recalculatePane(e,(0,J.sourceChangeEvent)(this.id())),
  this._model.updateSource(this)}
```
Не трогает `clearData`/`stop`/`start` (в отличие от публичного `restart(e)`,
который делает именно это — куда инвазивнее, ближе к remove+re-add по духу).
**НЕ вызывался вживую** — нет доступного искусственного stale-repro без
реальной правки продуктового кода (рискованно инструментировать на production
DEV ради теста), а сознательно имитировать баг сочтено неоправданным риском
без необходимости (см. `feedback_verifier_raw_chart_api_removed_indicator_incident`
— не импровизировать против internal API без веской причины и раскрытия).
**Рекомендация:** validate `recalculate()` СЛЕДУЮЩИЙ раз, когда реальный
stale-study инцидент произойдёт живьём (например, при возобновлении TM-331) —
не изобретать искусственный репро сейчас. Не готов как встроенный tool до этой
валидации.
